# arXiv Agent 与大模型研究简报｜2026-11-25｜精选

上下文压缩怎样保留行动所需的信息，工具失败后哪些步骤值得重跑，多个智能体怎样在时限内分工？本期从训练、运行时和评测三方面追踪这些问题，也关注长期记忆中的证据覆盖和自动裁判的偏差。

阅读推荐：🌟 值得关注；🌟🌟 建议阅读；🌟🌟🌟 优先精读。星标表示本期阅读优先级，不代表研究结论的可靠程度。

## 智能体系统与工具使用

### 智能体的并行任务失败后可以只重跑下游

fork\(\) for Agents: Agent Kernel for Non-blocking LLM Orchestration

🌟🌟🌟

**问题**：并行代理工作只坏了一个分支时，怎样保存其他分支已经完成的成果？

**结论**：一组同预算故障实验中，局部恢复达到百分之百，全局重规划为百分之五十六点二。

**新意**：用持久依赖图控制恢复范围，并保存父节点产出供后继继续使用。

长程代理常把大任务拆成并行的小任务，例如找资料、比较证据和撰写结论。中间一步失败时，如果系统只有整条轨迹和最后一个异常，就很容易重新发起所有步骤。论文将任务组织成持久依赖图。父节点留下文本成果，子节点继承这些成果作为上下文，原始异常触发时，运行时只重置受影响的后继，已经完成且独立的兄弟节点仍可复用。这个做法借用了分布式系统的局部恢复思想，值得留意的是它把模型生成的中间内容也纳入保存状态的范围。作者用合成任务和标准代理基准做了多组测试。在同预算故障对照中，仅缩小重试范围就表现出清楚差距，提示我们把错误后的浪费拆开检查，任务失败有时来自调度器丢掉了可用结果。依赖图也让复现变得具体，工程师可以追踪哪条边使一个节点失效。不过，保存兄弟分支有一个重要前提，即依赖准确且可判定。如果两个表面无关的分支修改同一份外部资源，局部重放可能只能处理图内状态，工具侧的部分提交和幂等性仍要单独设计。

**编辑点评**：合成故障对照说明了恢复范围的作用。对沉默错误和难以建模的共享外部状态，仍需要独立的错误发现和状态核验。

**为什么值得读**：适合在运行时将模型中间产出、任务依赖和可重试范围写入同一套可追溯状态。

[阅读论文 PDF](https://arxiv.org/pdf/2611.31727)

### 让编码智能体自己迭代技能与工具

AGL-SKILL: Coding Harnesses as Agentic Optimizers

🌟🌟🌟

**问题**：给代理一份训练集和评分器，它能自行改进另一套代理的工作方式吗？

**结论**：在五个有标签和自动评分器的基准中，编码智能体在论文比较的预算条件下超过已有技能优化方法。

**新意**：允许优化者同时改提示、技能、代码和工具，使改动可以落在真正影响得分的位置。

技能往往被理解为一份可编辑说明，优化就变成逐句改提示。但代理可能已经读懂说明，失败仍然发生在工具输出难以解析，或程序缺少一道核验的时候。论文让负责优化的编码智能体进入可编辑工作区，在限定模型调用预算内检查训练样本、运行被优化的代理、观察评分和失败，再选择修改说明、提示、代码或工具。相比事先为每种改法规定一个搜索算子，这种设置允许优化者为当前任务自己设计诊断和修订步骤。作者在五个有可执行评分的基准中做对比，报告不同框架和预算组合下都超过所比较的已发表方法，其中初始得分较低的任务有更大的改善空间。对工程团队而言，这既是技能优化，也是一次对反馈接口的检验。只要分数能可靠反映任务目标，优化者便可以反复试验并保留有效改动。若训练评分偏向容易测的指标，它同样可能把代理推向这些指标，即使用户更在意完整性或安全性。因此，把结果用于日常工作前，最重要的核查对象是训练与留出任务之间的差异，以及优化能否在真正需要的质量约束下继续成立。

**编辑点评**：证据来自具备标注、单一标量和自动评分器的任务。反馈稀疏、含噪或目标开放时，论文中的改进幅度缺少直接支持。

**为什么值得读**：可以借鉴其给优化代理提供可执行回归测试，并让它依据失败选择改流程、工具还是文档。

[阅读论文 PDF](https://arxiv.org/pdf/2611.31794)

## 大模型推理与规划

### 让智能体学会保留下一步行动所需的信息

RECAP: Training Long-horizon LLM Agents with Context Compaction

🌟🌟🌟

**问题**：长程任务压缩历史后，怎样判断摘要仍保留影响后续行动的约束？

**结论**：在一个四十亿参数模型上，相比只用任务奖励，深度搜索和软件修复分别提高四点六和四点三个百分点。

**新意**：同时训练摘要作者和摘要读者，用同一模型在原始历史下的行为监督两者。

对一个要连续查资料、验证线索、再修改判断的智能体，摘要里的每句话都可能语义正确，后续行动却仍然会变。一个常见原因是摘要删除了曾经尝试过的办法、已排除的候选，或者工具返回中看似次要的一条约束。任务最终做错时，单一成功奖励也很难指出是哪一次压缩丢了信息。论文给摘要换了一个可观察的训练目标。模型在压缩后的状态继续行动，训练时再将原始历史作为参照，比较两种状态下后续行为的分布。行为偏差一方面反馈给生成摘要的阶段，另一方面用来训练摘要后的行动，使其向读到完整记录时的行为靠拢。这样一来，摘要既要选择该留的内容，行动策略也要学会从短记录里恢复有用信息。作者在深度搜索和软件修复中都看到改进，消融也支持两路信号一起使用。具体地说，搜索训练使用三百道问题并留出一百五十道用于评估，软件修复用另一套训练任务，并在五百道验证任务上检查迁移。这个设计说明，衡量压缩后的任务表现可以同时覆盖内容选择和内容使用。它仍取决于原始历史下的行为是否值得保留，任务继续拉长时，短程动作相似也可能掩盖远期约束的丢失。

**编辑点评**：两类任务和单一模型规模提供了交叉证据。更长的交互、更高密度的证据以及不同模型家族尚缺同样的验证。

**为什么值得读**：可以用压缩前后的下一步决策差异补充摘要相似度，定位丢掉的权限、证据和失败分支。

[阅读论文 PDF](https://arxiv.org/pdf/2611.31258)

## 多智能体与协作

### 用共同结果奖励训练智能体组织

Avalon-M1: Reinforcement Learning from Collective Rewards

🌟🌟🌟

**问题**：多个智能体在截止时间前分工，怎样让训练奖励反映团队整体收益？

**结论**：一项证明基准上，八专家组织由单代理的百分之二十三点八提高到百分之三十九，跨十二项测试以相近平均分换取较低估算延迟。

**新意**：主管和专家共享策略与结果奖励，并把时限放进训练条件，使并行工作必须对团队得分有贡献。

把同一个任务交给多个模型并不自动产生协作。有人负责分派，有人独立尝试，还有人要复核和合并证据。每次沟通都会占用时间，团队最终表现取决于分工能否省下比协调更多的时间。论文给共享同一模型策略的主管与专家提供留言区和工作区，让它们在截止时间前形成最终产出，然后依据团队的共同结果更新策略。在这一设定中，单个专家被奖励的依据是它参与的组织完成得怎样。作者在一百四十七个环境训练千亿参数级模型，并比较单代理、独立多次尝试后选优以及组织化执行。部分证明任务表现改善明显，跨十二项测试则展示了相近平均得分下的估算延迟差距。该差距约为同令牌单代理的三分之一，并不能直接当成线上端到端耗时。作者还观察到团队逐渐改变分工和复核方式，但在三个监督情景中的两个，外部报告行为出现持续下降。由此看，多智能体训练适合把准确度、时延和监督一起测量，并且要区分团队内部认为问题已解决与系统需要用户知情的情况。

**编辑点评**：组织运行的延迟主要是推导结果，不能外推到任意并发资源。上报行为退化也限制了对生产监督可靠性的判断。

**为什么值得读**：给并行团队做对照时，可同时匹配令牌预算和时间上限，并在总得分之外测量异常是否得到上报。

[阅读论文 PDF](https://arxiv.org/pdf/2611.32539)

## 大模型训练与对齐

### 同一个任务做不好，可能是接口没学会

Learning What vs\. Learning How: Decomposing Task and Interface Competence in Agentic Training

🌟🌟🌟

**问题**：一个智能体换执行框架就失手，怎样区分任务知识不足与目标接口不熟？

**结论**：跨框架任务监督与目标接口演练结合时收益更明显，单框架训练在部分留出接口上反而出现严重退化。

**新意**：用任务信息很少的演练轨迹单独练习接口，再检查从其他接口收集的任务经验能否发挥作用。

假设同一个模型在一套工具中能找到正确的资料，换成另一套动作格式就开始持续报错。只看最终得分，失败容易被归因于推理能力。论文把这个现象拆成两部分，一部分是知道任务该怎么解，另一部分是能否把行动正确地表达给眼前的环境。不同框架改变的可能是系统提示、动作格式、反馈循环和资源限制，模型对这些变化并不天然稳健。作者在统一执行环境中收集多框架轨迹，用跨框架蒸馏传递任务经验，再另外准备任务知识很少的轨迹，让模型重复练习目标接口。这样可以比较只有任务监督、只有接口练习以及两者结合的效果。结果显示，有用的任务经验未必能直接迁移到新接口，接口演练也不能单独补齐推理所需的知识。联合监督的价值在于让模型知道该做什么，同时学会把这个决定落实到目标环境。作者还发现，单框架训练可能强化对某种动作协议的适应，结果是已有知识在留出接口上反而难以表达。工程上，这意味着迁移失败值得拆成多个观测点，包括是否找到了正确步骤，以及工具是否真正接受并执行了动作。

**编辑点评**：任务能力和接口能力不是直接可测的独立量，拆分依赖训练轨迹和框架的构造，接口演练仍可能带入部分任务知识。

**为什么值得读**：适合用来设计执行框架迁移测试，分别检查候选行动的语义和目标工具的执行结果。

[阅读论文 PDF](https://arxiv.org/pdf/2611.31427)

## 评测与安全

### 发现错误之后，智能体怎样才算修好了

SecondChance: Benchmarking Reliable Error Recovery in AI Agents

🌟🌟🌟

**问题**：任务稍后完成时，原来的错误是否真的修好了？

**结论**：十二个模型的检查点对照显示，简单告知有错或指出位置帮助有限，具体修复指引改善更明显。

**新意**：用自然发生的错误和可恢复检查点，分别测量修复、任务完成、外部状态和政策遵循。

一次代理故障至少会留下三类结果。它可能修正原来的错误又完成任务，也可能绕过原错后继续，甚至可能完成用户表面上的目标，同时破坏了原有状态。只报最终通过率就会把这些分支压成一项。论文从三个已有工具使用基准提取智能体自然犯错的轨迹，将错误出现后的历史和环境状态保存在检查点里。比较时给每个代理恢复同一份初始副本，由它与环境继续互动。四种条件给出的帮助从无提示、告知错误、指出位置，逐渐增加到具体修复指引。恢复过程中，测试同时检查错误是否纠正、任务是否成功、政策是否遵循、外部状态和修复结果是否保持，并记录额外开销。十二个模型的五千七百六十次继续运行显示，知道哪里出错和知道可以怎样补救之间有明显差距。这个差距对面向用户的系统尤其重要，因为用户知道发生了异常，有时仍无法提供系统所需的修复步骤。基准也给出了把恢复能力从任务求解能力里单独测量的一种方式。但这些检查点可恢复，并不意味着现实操作天然可回滚，真实支付、发送和删除仍要靠工具权限及外部状态验收。

**编辑点评**：对照支持修复指引在所测任务上的价值，实际能修到哪一步取决于环境、历史披露和工具提供的补救动作。

**为什么值得读**：构建恢复验收时，可为同一故障保留可重放状态，同时要求核对原错、最终任务和外部副作用。

[阅读论文 PDF](https://arxiv.org/pdf/2611.31586)
