# Commit Rules

## 目的与授权

本文定义本仓库的提交授权、粒度、消息格式、验证和历史安全规则。一个 commit 记录一个明确的工程判断或小步能力变化，不代表整项任务、草稿推送或阶段交付已经完成。

- 修改完成后默认保留在工作区；只有用户明确要求“提交”时才暂存并 commit。
- “提交”授权包含完成该提交所需的暂存，不自动包含 push、创建 PR 或合并。用户可以一次授权多项操作，已有明确授权持续有效，不重复确认。
- 用户只要求修改、检查或验证时，不自动提交。只提交当前任务范围内的文件，保留无关或归属不明的改动。

## 提交边界

- 一个 commit 表达一个可以用一句话说明的工程判断、能力变化、测试约束、配置装配或文档规则。
- 同一判断需要的代码、测试、配置、Skill、reference 和方案文档放在同一个 commit，避免形成互相冲突的中间状态。
- 不同判断、独立风险或可以独立理解、验证和回滚的变化拆成不同 commit。
- 不为减少提交数量机械 squash，也不为减少文件数量拆出无法独立理解或验证的提交；文件数量只辅助检查内聚性。
- 不混入无关格式化、重构、临时文件或用户已有改动。
- 成功草稿的 `repositories/publications/yyyyMMdd/<mediaId>/` 作为完整归档提交，包含稿件、封面、文案、稿件集和回执，不拆散归档内部文件。归档与生成器规则能够独立理解和回滚时，分成独立提交。
- 不改写已成功归档的旧稿来适配新规则；修订草稿按新回执另行归档。

## 提交消息

格式：

```text
Type(<project>[/<module>]): <中文工程判断>
```

- `Type` 使用 `Feat`、`Fix`、`Docs`、`Test`、`Refactor`、`CI` 等准确表达变化类型的名称。
- `<project>` 必须使用下表中的固定名称；可选 `<module>` 定位稳定模块或工作流，不使用临时简称代替工程名。
- 中文说明表达具体能力结果或规则结论，不以“调整”“修改”“优化”等泛泛描述代替工程判断。
- 必要时在正文解释不可拆分原因、验证结果和未覆盖边界；不复制文件清单或内部执行过程。

| project | 范围 | 边界 |
| --- | --- | --- |
| `repo` | 根 AGENTS、仓库治理、README、CI 及成功稿件归档 | 不用于论文处理和发布逻辑的实现 |
| `arxiv-paper-wechat` | 根 package 对应的论文处理与微信草稿工具，包括 CLI、Skill、reference、行为配置、方案及相关测试 | 同一能力的配套文档随该工程提交，不因文件位于 docs 而拆开 |

当前仓库没有登记多个独立运行工程，不引入 `cross-project`。新增独立构建、测试或交付的工程时，在同一初始化提交中登记固定名称与实际目录或 package 的对应关系；不得临时创造 scope。

示例：

```text
Feat(arxiv-paper-wechat/screening): 结合标题与摘要排序并递补下载候选
Feat(arxiv-paper-wechat/edition): 分别生成紧凑全览与深入精选
Docs(repo/governance): 建立按工程判断组织的提交规则
Docs(repo/publications): 归档 2026-09-04 微信草稿
```

## 提交前检查

1. 检查 `git status`，阅读完整待提交 diff，确认范围与本次工程判断一致；新文件也须检查内容。
2. 按 [AGENTS.md 的验证要求](../AGENTS.md#验证) 完成适用检查。检查后代码、配置及依赖未发生影响结果的变化时，可复用已有证据，不因提交动作本身重跑相同检查；未执行或失败的检查不得描述为通过。
3. 按 AGENTS 的事实来源同步行为、Skill、reference、方案和测试。若任务明确规定分步验收或固定提交边界，遵守该任务要求，不把未完成范围描述为完成；没有相关任务时不新建检查记录。
4. 只暂存目标文件，再阅读完整 staged diff，运行 `git diff --cached --check`。确认没有凭据、PDF、`.part`、`.tmp`、`.work/`、本地论文仓储、无关个人路径或其他临时数据。
5. 提交后回读 commit 与 `git status`，报告提交 ID、实际范围和剩余改动。工作区不干净时说明原因，不丢弃其他改动来获得干净状态。

## 历史安全

- 不自动 amend、rebase、squash 或重写已有提交；只有用户明确要求才能修改历史。
- 已推送或进入协作范围的历史，必须在用户明确确认范围和风险后才能重写；确需强制推送时使用 lease 保护，不使用无保护的 force push。
- 不使用破坏性命令丢弃用户提交、工作区改动或未跟踪文件。
- 不追溯重写旧提交以符合新消息格式；新规则适用于后续提交。
