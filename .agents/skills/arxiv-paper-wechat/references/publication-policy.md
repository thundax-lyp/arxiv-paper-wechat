# 稿件质量与编排规范

本文件是公众号成稿的质量契约：全览帮助读者快速筛选，精选帮助读者深入理解。`editorial.json` 保存完整研究判断、评分和核查记录，`copy.json` 保存独立撰写的发布文案；容量调整不得修改内部判断。

## 稿件集结构

- 发布稿总收录量最多 40 篇。CLI 按总分降序、arXiv ID 稳定选择，完整 `editorial.json` 保留所有 `keep` 判断。
- 精选只从入选的总分 `>=7` 论文中取前 6 篇；不足时宁缺毋滥。这些是内部选稿规则，不写入发布稿。
- 全览指本期入选论文全览，不暗示覆盖当天全部投稿；所有入选论文在全览中恰好出现一次，精选论文也包含在内。
- 每篇文章以简短导读介绍本期具体看点，按主题分组。CLI 内部沿用固定方向、分数降序和 arXiv ID 排序。
- 不固定每篇全览的论文数量。CLI 根据压缩后全览文案的保守源长度预算分篇，尽量保持同主题完整；主题本身超预算时在论文之间拆分，单篇论文不拆开。
- 不设置构建后的正文或手机排版复核关卡；通过程序检查后按用户授权直接推送微信草稿，由用户在手机上查看。所有文章均须经过真实微信公众号渲染器测量，逐篇不超过 100,000 字符。实测容量通过不等于阅读质量通过。

## 全览与精选

取消固定七栏，按读者理解顺序组织：遇到什么问题 → 方法怎么工作 → 实验发现什么 → 有什么价值与限制。

- `overview`：每篇约 100–160 字，写成紧凑短段落，包含研究问题、关键方法、主要发现和一条重要限制。
- `featured`：精选论文每篇约 450–700 字，独立撰写连贯叙述，补充背景、方法直觉、结果含义和具体限制；复杂论文可以适当延长。必要时可用有具体含义的四级小标题。
- 仅精选论文在英文原标题和星标之后、深入解读之前，依次醒目给出“**问题**”“**结论**”“**新意**”三项短述：分别界定具体缺口、最关键发现（含必要条件或代价）和相较已有工作的真实改变。它们帮助读者快速判断是否值得深读，不得写成内部评分或宣传口号。
- 精选的深入解读之后依次给出“**编辑点评**”和“**为什么值得读**”。前者说明证据支持到哪里、不可外推的边界或主要风险；后者说明即使存在局限，该工作对研究设计、系统实现或评测实践的具体启发。两者不得互相重复，也不得套用泛泛模板。
- 上述五项只属于精选；全览保持紧凑短段落，不增加固定栏目。
- 精选不复制全览，也不把全览和内部七栏直接拼接；增加的是解释，不是参数和术语。
- 字数仅为编辑参考，不设机械字数门槛，不为凑字数补内容，也不为压缩删掉关键条件。

## 读者需要看到什么

发布稿删除数值评分、评分规则、论文序号、关键词、作者／机构未确认等内部核查状态，以及核查数量、筛选流程、“稳定选取”等生产说明。不使用重复目录表格、机械重复的栏目标题和装饰性 emoji；推荐度仅使用 🌟。

作者和机构不再是每篇必填展示项；只有帮助理解研究时才自然写入正文。核查记录留在内部材料中；缺失信息若影响结论可信度，应解释它造成的具体证据限制，而不是展示“未确认”状态。

## 原标题与推荐度

每篇中文标题下展示 `list.json.title` 中的英文原标题，保持纯文本，不设链接；不得自行翻译回英文或编造原标题。随后单独显示推荐星标，正文末尾保留“阅读论文 PDF”。

`copy.json.recommendationLevel` 必须为整数 1、2、3，依次显示 🌟、🌟🌟、🌟🌟🌟，分别表示值得关注、建议阅读、优先精读。LLM 根据读者相关性、解释价值与阅读投入给出优先级，不机械换算内部总分，不强制各档数量。同一论文在全览和精选中使用同一推荐度。整期首篇文章的导读后解释一次星标含义，论文条目只显示星标；不展示数值或计算规则。星标表示本期阅读优先级，不代表研究结论的可靠程度；具体证据限制仍写在正文中。

## 语言与证据

- 开头直接解释问题或发现，不先介绍一串方法缩写。用动作、先后关系和必要示例解释机制，减少名词堆叠；必要术语首次出现时简短解释，修正生硬直译。
- 中文标题突出具体问题或发现，保持纯文本，不强制逐字翻译英文原标题；不得夸大结论或使用营销话术。
- 删除泛泛的“意义重大”“仍需进一步验证”，改成具体价值和具体限制。
- 只根据当天论文 Markdown 和已校验的 `editorial.json` 写作。缺失信息回查原论文；仍无法确认时不自行补全。
- 优先呈现一组关键结果，必要时补充代价或反例。交代指标、比较对象和必要实验条件；区分相对提升与百分点、模型评分与实际效果、容量验证与质量验证。
- 保留会改变读者判断的限制和解释结论所必需的证据；详细超参数、次要消融留在内部材料。语义压缩先删重复背景和修饰语，再压缩次要实验，不得把不确定性改成确定事实。

## 链接

每篇默认只保留“阅读论文 PDF”，由 CLI 使用列表中的 PDF URL 放在所属论文内容末尾、下一篇标题之前。标题不设链接；正文不手写重复 PDF、arXiv 摘要页、代码仓库或项目主页等固定入口。

仓库本身是解读核心时才填写 `copy.json.codeLinkReason`，说明为何需要代码入口；CLI 使用已核实的 `editorial.json.codeUrl` 追加代码链接。该理由是内部记录，不展示在正文中。

## 生成与草稿检查

事实依据、解释质量和证据边界在阅读与撰写阶段落实，不另设构建后的正文复核步骤。CLI 检查字段、明显的整段复制、覆盖、链接与容量；通过后按用户授权直接创建微信草稿。无需打开浏览器或模拟手机预览，用户在微信草稿中查看正文与排版，再提出修改。

## 封面联动

封面 brief 使用精选论文；无精选时使用最高分保留论文。视觉主题由当日研究内容抽象而来，继续遵守无文字、无 logo、无真实人物和 `21:9` 的硬约束。

渲染和草稿发布统一传入 `--no-cite`，关闭外链编号与文末重复链接汇总，保留每篇末尾的 PDF 入口。`edition measure` 在 Markdown 旁保存本次实测的 HTML，供排错留存，不作为推送前人工复核关卡。
