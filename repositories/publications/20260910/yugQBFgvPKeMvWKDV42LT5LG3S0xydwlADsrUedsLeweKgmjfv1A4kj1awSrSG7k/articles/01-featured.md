# arXiv Agent 与大模型研究简报｜2026-09-10｜精选

这期集中看智能体怎样挑选可执行工具、核对程序义务，以及让记忆和多模型协作更可控。另有研究提醒：答案暂时稳定不等于推理已完成，过程证据比最终分数更能解释成败。

阅读推荐：🌟 值得关注；🌟🌟 建议阅读；🌟🌟🌟 优先精读。星标表示本期阅读优先级，不代表研究结论的可靠程度。

## Agent系统与工具使用

### 工具列表要把前置步骤排进来

The Menu Is an Execution Prior: State-Path Tool Menus for Online Agents

🌟🌟🌟

**问题**：短工具菜单只按当前请求相关性排序，常把最后一步展示出来，却漏掉生成其输入的前置工具。

**结论**：在ToolBench中按状态路径构造菜单，将在线成功率从0.737提高到0.898；前提是工具文档和路径历史足够可靠。

**新意**：把工具菜单视为执行路线的先验，联合选择可执行入口、输入生产者和最终动作并排序。

一个智能体想完成多步任务，看到的工具不能只有“提交结果”按钮；它还得先看到查询、转换或验证等产生必要输入的工具。传统检索器按请求和工具描述的相似度给出短列表，最终动作往往最相关，前置动作反而被挤走。论文把当前可观察状态、工具输入输出关系和历史调用顺序编码为状态路径。检索器覆盖路线中的入口、缺失输入生产者和最终动作，重排序器再把生产者放在消费者之前。在线智能体本身保持不变，只替换它最初可见的菜单。ToolBench主结果中，成功率由0.737升至0.898；论文还报告32个工具形成的完整链覆盖优于官方128工具列表，并在其他工具库与执行器上检查稳定性。这个结果说明菜单的价值不只是“哪些工具有关”，更在于“能否从现在的状态执行到目标”。不过菜单在第一步前固定，执行中若观察带来新条件不会自动更新；输入输出字段贫乏、历史路线稀疏时，依赖关系也会变得难学。

**编辑点评**：提升来自所测工具库的在线任务，尚不能保证新工具文档或动态环境中的路径同样准确。

**为什么值得读**：构建工具检索时，可把前置输入与调用顺序纳入评测，而不是只测工具名称召回。

[阅读论文 PDF](https://arxiv.org/pdf/2609.09395)

### 用语义关系整理冲突和重复的智能体记忆

ROAM: Robust Organization of Atomic Memories for Agents through Semantic Relations

🌟🌟🌟

**问题**：长期记忆里重复、冲突和过期的短事实互相竞争，检索可能把旧记录误当现状。

**结论**：关系引导的主记录与证据分层在受控评测中提高回答准确率，最大增幅29.8个百分点；效果依赖检索预算。

**新意**：模型只判断原子事实之间的语义关系，存储状态转换由确定性规则执行，并保留可审计原始观察。

很多智能体记忆系统让模型直接决定添加、改写或删除一条事实。这个步骤把“理解新旧事实关系”和“改变数据库状态”混在一起，遇到纠正、补充或时间变化时容易产生错误。ROAM先把观察拆成原子记忆，比较新旧记录是独立、等价、单向包含还是冲突。模型负责这个受约束的语义判断；系统规则决定哪些记录是当前主视图、哪些保留为支持证据。随后融合过程把互补细节和时间变化整理成更紧凑的检索视图，但原始观察不被丢掉。回答时只检索主视图，避免重复或过期片段各自抢占有限上下文。论文在受控干扰、LongMemEval和MEME-Post设置中比较了多个记忆管理基线，报告最高29.8个百分点的准确率提升；消融显示关系管理是主要贡献，融合另有增益。这里的百分点来自特定模型、历史与预算组合，不是所有应用的预期收益。真实部署中的更新频率、长期流长度和关系判错，都可能改变主视图质量。

**编辑点评**：基准历史与固定预算让干扰可测，但不能覆盖真实持续更新；语义关系误判仍可能把有效证据压到次要层。

**为什么值得读**：设计记忆层时，可把模型判断与状态变更分开，并保存来源以便纠错和追溯。

[阅读论文 PDF](https://arxiv.org/pdf/2609.09778)

## LLM推理与规划

### 答案反复一致，推理也未必结束

Stable Answers, Unfinished Reasoning: Why Self-Consensus Is Not a Safe Early-Exit Signal

🌟🌟🌟

**问题**：推理模型中途反复给出同一答案，可能只是暂时占位，尚未完成会改变结论的思考。

**结论**：3520种自一致停止规则没有同时通过预设安全和节省门槛；一个非一致性边界信号对照通过。

**新意**：把“答案暂时稳定”与“推理真正终止”拆开测，并预注册规则搜索与成本门槛。

为了节省推理token，可以在一条尚未完成的轨迹上不断询问模型当前答案，看到多次一致就提前停。但这种一致只说明在固定探针下答案保持不变，不能说明后续推理不会修正它。论文保存两个模型在三个数学基准上的完整轨迹，再离线重放3520种停止规则，按预先设定的精度损失与节省比例检查。没有一条自一致规则同时通过三个接受门槛；留出切分与两个未见模型重现了这个边界。一个仍节省32% token的规则约九次停止有一次落在模型后来主动放弃的答案上，且多数截断了本来会发生的纠错。把一致窗口拉长，这类非终止停止比例仍趋近约7%，而节省降到8%。论文也把不读取一致性的边界置信度方法放入同一管线，对照通过门槛。结论针对固定探针、冻结轨迹和数学任务；它不是说所有提前停止都不安全，而是说“同一条推理当前答案重复出现”本身不足以作为终止证据。

**编辑点评**：负结果依赖测试的探针和任务，边界方法同时改变检查位置与统计量，不能把优势全归于单一信号。

**为什么值得读**：优化推理成本时，应把后续自行修正率列入停止指标，而不只记录当前探针的一致率。

[阅读论文 PDF](https://arxiv.org/pdf/2609.09989)

## 多智能体与协作

### 多模型结果能否由明确规则合并

UnitBoost: Managing Compound LLM Systems with a Merge Operator, Not a Model

🌟🌟🌟

**问题**：让一个生成式元智能体同时合并工人结果、分配新调用和决定停止，会使控制过程不透明。

**结论**：单元合并算子在多个知识任务中超过输入匹配的生成管理者；任务若难以拆成可靠单元，收益会减弱。

**新意**：让模型提出候选片段，确定性算子负责采纳、组合和识别未填缺口，下一轮只围绕缺口工作。

多个工作模型分别找到一部分答案时，常见做法是再请一个强模型读取所有结果，写最终答案并决定下一轮查什么。它灵活，却会把来源选择、组装和停止放进一次难审计的生成。UnitBoost把任务先拆成可检查的单元：工作模型的输出变成带来源的槽位提案，算子在约束下挑选有支持的值，未填或证据不足的槽位形成下一轮的明确残差。没有单元耦合约束时，逐单元最大化在同一采纳分数下有简单的候选选择上界；有耦合约束时仍需修复。三个留出基准里，它比用金标准标签挑的最佳整份候选高出0.060到0.195个绝对任务分点，也高于输入匹配的生成式管理者。把管理环节替换进六种复合系统同样有正收益；残差引导让FanOutQA的cell F1由0.4778升至0.5524。结果的代价与条件很清楚：任务必须能定义稳定单元，评分函数必须可信，代码这类高耦合任务可能让组装修复变贵。算子可审计，并不意味着错误的采纳准则会自动纠正。

**编辑点评**：主要正结果来自知识密集语言任务；单元定义和评分若不可靠，确定性合并也会稳定地产生坏答案。

**为什么值得读**：多模型系统可先试着显式记录每个答案片段的来源、缺口与停止理由，再判断是否需要生成式管理。

[阅读论文 PDF](https://arxiv.org/pdf/2609.09815)

### 技能何时适合交给子智能体执行

Subagents vs Agent Skills: Executing Reusable Knowledge for Long-Horizon Agentic Tasks

🌟🌟🌟

**问题**：长任务中把整份技能说明放进主上下文，可能让智能体在积累工具轨迹后更难执行。

**结论**：有明确输入输出契约的程序技能适合由子智能体独立执行；缺少契约时优势不成立，而且总 token 开销增加。

**新意**：把技能从“给主智能体读的说明”改为“可调用且能交付结果的独立过程”，并实验比较上下文峰值。

技能包通常由说明、脚本和资源组成。传统调用把说明加载到主智能体，它仍要自己完成后续步骤；任务越长，主上下文越容易被工具记录和其他约束占满。论文提出另一种执行方式：主智能体给子智能体一个具体任务，子智能体在新上下文里读取技能包、完成任务，只把结果返回。这减少单个上下文的峰值长度，却要重复传递必要输入。研究者在SkillsBench上区分原有技能与按成功轨迹整理的程序技能。前者往往没有清楚的交付契约，主智能体直接读技能表现持平或更好；后者明确了输入、输出和操作步骤，子智能体才获得优势，较小模型受益更明显。论文还增加无关工具来提高上下文压力，并分别计量峰值上下文与总token：收益来自把程序封装到独立上下文，代价是通信。结论因而是条件性的。一个需要多个技能交叉推理、或交付物难以界定的任务，拆出去可能丢失主上下文信息；技能作者必须先把接口与完成条件写清楚。

**编辑点评**：对比只在测试的技能包与智能体框架中成立；原始技能未显示子智能体优势，不能把委派当成通用优化。

**为什么值得读**：设计长任务工作流时，可先检查技能是否有可验证的输入输出，再决定是否让独立智能体执行。

[阅读论文 PDF](https://arxiv.org/pdf/2609.09233)

## 评测与安全

### 程序看似完成时，如何发现漏掉的义务

ContractEval: Query-Conditioned Execution Matching for Procedural Instruction Conformance

🌟🌟🌟

**问题**：程序型智能体可能给出看似正确的答案，却跳过了查询实际触发的检查、分支或不变量。

**结论**：金标准预期与观察图可定位受控注入的全部结构失败；LLM自动抽取保留部分效果，但仍不是合规保证。

**新意**：把评价单位从整份答案改成“当前查询激活的义务及其执行证据”。

例如一份操作流程要求先核验权限，再按条件选择分支。只看最终文本，智能体即使绕过核验也可能给出合理结论；把轨迹交给另一模型评审，也未必知道此时究竟哪些义务必须发生。ContractEval先把程序说明表示为义务，再根据具体查询选出当前激活的条目，对照响应或轨迹中的证据。它区分遗漏、错误分支、顺序颠倒、多余动作、不变量破坏和输出契约违背。论文构建10份流程式契约、每份20个查询，得到200个干净执行，再注入六类扰动形成1400个案例。普通答案评审平均只发现约半数控制失败；最强的轨迹评审在扰动案例中仍漏掉29%。给ContractEval使用人工确认的预期与观察图时，受控失败全部能定位。自动用LLM抽取图更接近实际部署，却会受到提示、模型和校准影响。这里的核心不是让某个评审模型说“通过”，而是先明确可检验的义务，再让证据逐项对上。它提高审计可解释性，但图抽取错误和不完整轨迹仍能漏掉真实违规。

**编辑点评**：全数定位仅限金标准图与受控扰动；自动抽取和真实流程的复杂性不支持合规保证。

**为什么值得读**：对有SOP或安全步骤的智能体，可先把每个查询的必经义务显式化，再设计轨迹审计。

[阅读论文 PDF](https://arxiv.org/pdf/2609.09458)
