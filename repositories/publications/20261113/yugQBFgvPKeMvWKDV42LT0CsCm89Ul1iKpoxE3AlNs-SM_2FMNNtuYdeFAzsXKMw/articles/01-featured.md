# arXiv Agent 与大模型研究简报｜2026-11-13｜精选

本期从三个实际问题看智能体怎样工作：交接记录是否对应真实状态，工具动作有没有经过防护，写出正确补丁后还需不需要继续。另有研究拆解共享文档推理的显存开销、蒸馏目标中的冗余，以及检索引用与生成来源的差别。

阅读推荐：🌟 值得关注；🌟🌟 建议阅读；🌟🌟🌟 优先精读。星标表示本期阅读优先级，不代表研究结论的可靠程度。

## 智能体系统与工具使用

### 日志写成已修复，现场的错误仍会拖累接手者

Cleaning an Agent's History Hurts When the World Still Holds the Error

🌟🌟🌟

**问题**：交接记录改写后，接手者还能分清哪些工具动作真的生效了吗？

**结论**：当写入实际未生效，成功回执使整题成功率从45%降至28%。写入实际生效时，方向反过来。

**新意**：恢复任务的同一个中途快照，分别改动交接记录和环境状态。

设想一个智能体把错误金额写进数据库。后来系统查到了正确金额，准备把任务移交给另一个模型。它可以保留失败动作，附一条说明告诉接手者应当填什么。也可以直接把旧记录修成一条看似已经完成的正确写入。两份记录都包含正确金额，接手者需要做的事却不同。

论文把任务冻结在能够恢复的中途状态，让接手模型沿修改后的轨迹继续。第一组实验保留环境里的错误值。与内容无关的匹配提示相比，保留旧动作并附上正确值让后续目标恢复率从51%提高到66%。把正确值写成智能体已经完成的动作，则让恢复率从原始记录下的50%跌到44%。两个数字的比较对象不同，不能直接合并为同一个干预效果。

第二组实验把数据库是否含有写入结果与回执是成功还是失败分开操纵。写入结果不在时，成功回执比失败回执更容易让接手者跳过待办，整题成功率从45%降至28%。写入结果在时，相同的成功回执把成功率从38%提高到49%。设计把文本和环境的交互显露出来。交接质量可以看新记录是否让模型找到仍待完成的动作，还可以查操作在外部系统里是否产生了应有的状态变化。

**编辑点评**：两个可恢复环境支持这组反事实比较。第一组的消息角色与记录真假未完全交叉，不能把差异全部归到措辞。

**为什么值得读**：可以据此设计交接测试，把外部副作用、回执和待修复事项作为独立可核查的状态。

[阅读论文 PDF](https://arxiv.org/pdf/2611.14654)

### 压缩智能体历史时，给每段原始证据留一个入口

Folio: Recoverable Multi-Resolution Context Folding for Long-Horizon Language Agents

🌟🌟🌟

**问题**：上下文预算变紧时，智能体怎样保留回到原始工具证据的能力？

**结论**：同一底座和运行时的对照中，折叠历史解出66道长程任务，模型摘要解出54道。

**新意**：边执行边记三层历史，压缩只选择已有视图，并保留统一的证据句柄。

长程任务中，一次工具调用可能返回几千行内容。后续只用到其中一小段，但模型要找到那一段时，历史可能已经经过几轮摘要。把整段上下文重新交给模型压缩需要额外推理，也可能把当时看似无关、后来成为关键的证据合并掉。

论文让智能体每轮留下短记，运行时同时登记每个事件以及对应原文。三个层级使用相同的定位入口。遇到预算压力，系统选择在上下文中留下哪些短记、哪些事件清单以及哪些原文片段。当前视图可以变粗，句柄仍能让后续工具按页取回证据，或对保存在文件里的完整内容做计算。选择保留视图时，系统还能提前算出折叠后实际占用的预算。

在75项长程任务中，作者用相同主底座比较多种系统。折叠方案解出66题，同一运行时改为模型摘要后解出54题，折叠操作的中位耗时为0.6秒。这个对照把问题从谁写出了更好的摘要移到历史有没有留下可用入口，以及必要时能否及时找回原文。对工具使用密集的任务，值得分别测量归档的存储和读取成本、回查时拿回的词元量，以及关键信息在多次折叠后是否仍能定位。

**编辑点评**：结果主要来自一个模型和一个长程基准。短记仍会漏掉信息，回查工具本身也消耗时间和上下文。

**为什么值得读**：对需要保留证据链的智能体，可以分别设计历史视图和原始记录的访问方式，再用预算对照测量效果。

[阅读论文 PDF](https://arxiv.org/pdf/2611.16627)

## 大模型推理与规划

### 同一份长文有很多问题，解码时可以少读几遍

Read Once, Answer Many: Parallel Prompting for Shared-Context LLM Inference

🌟🌟🌟

**问题**：几十个问题共享长文时，为什么用了前缀缓存，解码仍可能被带宽限制？

**结论**：单卡离线实验中，长文有64至256个独立问题时，相较标准引擎约快3.7至6倍。

**新意**：将多个独立答案合进同一请求，注意力内核一次读取共享文档，再隔离各自的答案流。

一批问答围绕同一份长文，服务端可以预先把文档读入缓存，免去为每道题重新计算前缀。到逐词生成答案时，每道题仍要对文档做注意力。如果引擎按独立请求调度，每个生成步骤可能又从显存反复读取同一份文档缓存。文档越长、问题越多，重复读取越容易成为瓶颈。

论文将多个独立问题放进同一个请求，为每个答案流分配编号。注意力内核根据编号决定哪些位置可见：每条流可以看共享文档、自己的问题和已经生成的答案，彼此隔开。这样解码一步只需把长文缓存读取一次，同时更新多条流。这个掩码直接在内核计算，无需额外存一张稠密掩码，每步的形状也保持固定。

对约八千到一万六千词元的文档，每文安排64至256个问题，在两个软件版本和两种显卡的离线对照中，作者报告约3.7至6倍加速。读长文、答短题时，省掉的重复读取占比较大。答案很长、不同答案完成时间差别很大，或者请求陆续抵达时，系统未必能在每一步凑齐足够多的并行流。部署前应先看共享文档的请求能否成批，以及现用内核的显存访问是否真是瓶颈。

**编辑点评**：实现只覆盖一种注意力后端、单卡和贪心解码，在线调度未测，数字对应论文的共享文档批量设置。

**为什么值得读**：这项工作给长文问答提供了一个具体的性能诊断：区分预填充复用与每步解码的缓存读取。

[阅读论文 PDF](https://arxiv.org/pdf/2611.15130)

## 评测与安全

### 编码智能体写出正确补丁后，还要多久才停

Termination Lag: Coding Agents Solve Early but Stop Late

🌟🌟🌟

**问题**：只看最终补丁，如何知道编码智能体何时已经解出了题？

**结论**：部分模型配置的成功轨迹中，首次正确补丁之后的步骤中位数占35%至60%，少量轨迹还会改坏补丁。

**新意**：沿轨迹逐一重放不同的代码补丁，定位首次通过与最终结束之间的间隔。

编码智能体完成一次编辑后，通常还会跑测试、看周边代码，或者继续改动。最终提交若通过测试，我们很难从这一个结果知道额外操作是否有必要。作者为每次源码编辑生成可还原的补丁，之后逐一在基准环境中跑相同的测试。这样，同一条轨迹就有了两个可比较的时刻：第一次留下通过测试的补丁，以及执行真正停止。

研究覆盖五种模型、两套执行框架和三个软件修复基准。成功轨迹中，38%至82%在第一次源码编辑时已经解出。所报告的核心设置里，一类模型在解出后仍有35%至37%的中位步数，另一类达到54%至60%。这些步骤多用于验证和继续查看仓库。少量情况下，后续修改还撤销了原先正确的补丁，最终评测变成失败。

这给停止策略提出了一个具体任务：系统能否用执行当时拿得到的证据判断补丁已经足够，并留住已通过检查的版本？离线基准的完整测试是研究者回放时的标尺。在线系统可能只知道局部测试过了、用户需求未全部覆盖，或者已有测试本身不可靠。采用同样的时间轴，可以测量一种停止策略究竟省了多少步骤，以及省下的步骤中有多少原本会发现遗漏。

**编辑点评**：每个任务只运行一次，步数是活动量的近似。不同操作耗时差异大，不能把步数比例直接当成成本比例。

**为什么值得读**：把首次可接受补丁与最终交付分开记录，可以同时评估提前停止、验证开销和回退策略。

[阅读论文 PDF](https://arxiv.org/pdf/2611.14960)

### 网关看见工具调用，能看见智能体的其他动作吗

guardscope: Measuring Which Actions Runtime Controls Check in LLM Agent Systems

🌟🌟🌟

**问题**：智能体用工具之外的方式改变环境时，网关能检查哪些实际动作？

**结论**：源码枚举覆盖十五类路径，参考负载实际验证四类，能据此识别经过控制点和绕开控制点的动作。

**新意**：用内核记录与控制决策日志对账，将受检、绕过与被阻断分开。

一个工具网关可以看见它代理的调用。若工具启动了子进程，子进程又读文件或发送请求，后面的动作可能已经越过这个观察点。研究者将问题落实成可测量的覆盖：动作究竟有没有经过一个具备检查能力的控制点，或者是否已被更早的隔离阻断。

论文分两阶段。先看框架和防护实现，画出动作可能走的路径，按控制的放置位置预测哪些路径会被检查。然后实际运行固定负载，采集两份记录：一份来自防护层的决策日志，一份来自系统内核观察到的活动。按事件对账后，可以把确实进入检查的动作、执行但没有经过检查的动作，以及被阻断的动作分开。由此还能检查静态推断与部署行为有没有分歧。

实验用了两套智能体框架和真实的运行时控制，其中参考工作负载实际走过十五种路径中的四种。其余路径仍由设计分析覆盖。即便某个动作在日志中被记为受检，还要另测规则是否能识别攻击，以及是否会错误地拒绝正常任务。对准备接入新工具的团队，这套方法可以用来检查工具和执行环境之间的整条路径，尤其是工具内部触发的系统动作。

**编辑点评**：目前实验只覆盖部分动作路径，内核事件也需要与应用动作准确关联。覆盖结果无法直接给出安全防护效果。

**为什么值得读**：它把网关的能力声明变成可复核的问题，可以具体指出哪条路径受哪一处控制。

[阅读论文 PDF](https://arxiv.org/pdf/2611.15223)

### 给小模型智能体限制写入权限，从工具定义开始

CapLite: Prompt-Injection Defense for Small Language Model Agents without Model-Written Security Artifacts

🌟🌟🌟

**问题**：小模型写出的安全规则也可能出错，怎样限制它对外部系统的写入？

**结论**：单一基准的13935次带攻击回合中无成功攻击，攻击下任务效用为29%，较未防护组低。

**新意**：由运行时从工具参数定义推导写入规则，并在读取不可信工具结果前锁定写操作。

邮件、网页和文件可以含有伪装成指令的内容。模型读完之后如果还能自由决定发给谁、修改哪个对象，文本就可能改变写操作的目标。论文先比较让智能体自己写权限策略、依赖关系或约束的做法，发现小模型产出的安全规则可能漏掉攻击，也可能生成不能执行的程序。

作者的方案在读取工具结果之前确定允许做哪些写入，再依据工具结构判断哪些参数会决定操作影响谁或什么。收件人、金额、对象和目的地等值只有能在用户请求中找到授权时才放行。工具结果可提供任务所需资料，但无法为写操作补出新的授权。假如用户没有明确说明这些值，流程就需要补确认，因而一些正常任务不能直接完成。

在十五个开放权重模型、同一个攻击基准的13935次带攻击回合中，作者没有观测到成功攻击。防护后的攻击下任务效用为29%，未防护组为50.2%。这两项应一起读：把权限约束落到工具结构可以获得明确的写入边界，也会限制需要根据查到的信息才能确定目标的任务。评估实际工具时，可以逐项检查影响对象的参数能否完整识别，再测试哪些正常工作流需要额外授权。

**编辑点评**：基准只覆盖一组环境，保护范围依赖工具定义与关键参数识别，实验结果不能当成所有部署的攻击成功率。

**为什么值得读**：论文展示了如何把写入授权变成运行时可执行的条件，便于小模型系统同时测安全性和任务完成率。

[阅读论文 PDF](https://arxiv.org/pdf/2611.17115)
